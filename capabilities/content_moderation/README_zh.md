# 用 Claude 执行内容政策

把成文的内容政策转化为程序可执行的规则。

## 问题

内容审核是在内容发布前对照成文政策检查内容，然后决定如何处理：发布、拒绝，或送交人工审核。内容可能来自任何地方。用户发表评论，卖家创建商品列表，广告主提交创意素材，你自己的市场团队起草需要法务放行的营销活动。政策是由政策、法务或品牌团队用通俗英语写成的文档。内容持续到达，数量往往超出任何人工团队的处理能力。

审核有真实的约束。判定必须一致：两份完全相同的提交不能得到不同的结论。拒绝必须可解释，因为提交者会申诉，监管方会追问。而政策会不断变化（新的州法规、新的诈骗类别），所以执行它的机制也必须能安全地随之变化。

## 常见做法

用 LLM 的自然首个构建是把整份政策文档放进提示词，追加内容，然后请求判定。它作为原型不错，在演示里也能工作。但在生产量级上它会撞上上述全部三个约束。同样的内容在不同次运行中可能得到不同判定。拒绝的理由只是模型恰好生成的那段文字，审核者无法逐行核对。而政策变更只是一次提示词编辑：没有可评审、可比较差异、可回滚的东西，并且每一次过往判定都是在无人记录过的某个提示词版本下做出的。

## 本 Cookbook 的替代做法

Claude 只在两个确切的位置运行，而这两处都不决定判定结果：

![Architecture: authoring compiles policy prose into a validated, versioned ruleset; runtime extracts typed fields from each submission and a pure-function rule engine produces the verdict](images/architecture.png)

- **编译器**把每条政策条款转化为由你定义的模式（schema）之上的规则。
  一个静态校验器把每条规则对照模式检查，并把问题交回给 Claude 修正。需要判断力的条款（"没有人看起来小于 25 岁"）变成在抽取阶段被回答的判断型字段。完全无法检查的条款会被列为不可编译，而不是被悄悄丢弃。
- **抽取器**把每次提交——文字和图像——读取为带类型的字段，用一次
  API 调用完成。这次调用就是每次审核的全部成本。
- **引擎**约 200 行纯 Python，没有任何模型调用。它把
  规则应用于字段并产出判定，并给出一份显示哪些规则触发以及为何触发的追踪记录。同样的输入，每次都是同样的判定。规则可以限定适用范围（"仅在新泽西州"），而当模型无法确定某条规则所需的信息时，该提交会送交人工审核，而不是得到一个猜测。在不同适用范围或新的规则集版本下重新检查内容不产生成本。

从 **[guide.ipynb](guide.ipynb)** 开始。它已完整执行，你可以不运行任何代码就直接阅读输出。

## 这里有什么

这套模式不局限于某一种内容。任何对照成文政策检查内容的场景都适用：商品列表、广告创意、评论与点评、招聘信息、卖家资料、视频和播客的元数据、正在走法务或品牌审核的市场文案。本 Cookbook 端到端跑通了其中三类：

| 路径 | 它是什么 |
|---|---|
| `guide.ipynb` | 本 Cookbook：模式、规则语言、引擎、编译器、LLM 断言、抽取、从通俗英语添加规则、领域替换、评估 |
| `engine.py`、`pipeline.py` | 规则引擎和两个 Claude 阶段；指南导入它们并展示其中关键部分 |
| `data/ad_creatives/` | 完整示例：模式、政策文档、一份手写的参考规则集、带标签的样本，以及合成的创意图片（`build_creatives.py` 可重新生成） |
| `data/product_listings/` | 第二个领域：市场平台商品列表（假货、医疗声明、平台外支付、卖家等级规则） |
| `data/ugc/` | 第三个领域：评论与点评（骚扰、个人身份信息、垃圾内容） |
| `evaluation/run_eval.py` | 针对三个领域全部带标签的样本运行整条流水线 |

数据中所有公司和品牌都是虚构的，创意图片用 Pillow 生成，因此基准答案标签按构造即为正确，这里没有任何内容像真实的广告主。

## 效果如何

在三个领域的 22 个带标签样本上，流水线做对了 21 个判定。唯一失误是一条确实处于边界情形的评论（一个新账号链接自己的博客：算推广还是不算？），笔记本解释了它为何发生以及如何修正：你打磨的是模式中某一条字段描述，而不是规则或引擎。

## 运行它

```bash
# from the repo root (or standalone: pip install anthropic python-dotenv)
uv sync --all-extras
# from capabilities/content_moderation/, runs the full 22-sample evaluation:
python evaluation/run_eval.py
```

笔记本自身的评估单元格默认每个领域只跑 2 个样本以控制成本；设置 `RUN_FULL_EVAL=1` 可得到完整表格。默认的笔记本运行约需 10 到 15 分钟，成本大约一美元。

## 何时使用这套做法

它适合以下情形：政策属于你且经常变化，判定必须向提交者或审计方解释，同一内容会在不同适用范围或政策版本下被反复检查，以及拥有政策的人不是工程师。

对于 CSAM 或暴力这类标准的单类别检测，它是错误的工具，专门的分类器才是合适选择。对于没有政策变更需求的单次分类，它又过重，单个分类提示词就能完成任务。
